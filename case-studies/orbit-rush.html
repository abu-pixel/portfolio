Orbit Rush

A fast arcade dodge-and-collect game with physics, combos, dashes and unlockable trails — one shared engine running in the browser and as a native mobile app.

01Project overview

Orbit Rush is an arcade game where you dodge obstacles, collect pickups, chain combos, use a tactical dash and unlock trails. The web version renders with HTML5 Canvas in React; the mobile version is an Expo and React Native app with haptics. Both run the same game engine, and both talk to an Express API through generated, type-safe clients.

02The real problem

I wanted to build a game that ran well on a phone and a laptop without writing it twice, and to practise strict type safety across a project larger than a single file. The risk in that setup is drift: change the API and one client silently keeps the old shape. The architecture is built around removing that drift.

03Target users and their needs

  • Players who want a short arcade session in a browser or on a phone, with no sign-up to try the web version.
  • Input that fits the device: keyboard and mouse on the web, touch and haptics on mobile.
  • Consistent rules and progression regardless of which client is used.
  • For me as the developer: one engine to maintain and a contract that catches type mistakes early.

04System architecture

05Technology selection and justification

  • pnpm monorepo: keeps the engine, web client, mobile client and server in one repository with shared packages.
  • TypeScript everywhere: the same rules and data shapes are checked across all four parts.
  • React 19 and Canvas: a familiar UI layer around a render loop that needs direct drawing control.
  • Expo and React Native: reuse the engine on a phone while adding touch input and haptics.
  • OpenAPI plus Orval and Zod: the API document generates React Query hooks and runtime schemas, so a server change shows up as a client type error instead of a production surprise.
  • Express with Drizzle ORM: a small typed server for game data.
  • Tailwind CSS: fast, consistent styling for the web shell around the canvas.

06Database schema / data model

The server stores the data shared by the two clients. I have not published a schema document for Orbit Rush, so I will not name tables or columns here. The Drizzle schema in the repository is the exact definition; this case study describes the model only at that level of detail.

Ownership

The monorepo contains the engine, web app, mobile app and server as separate packages.

Contract

The OpenAPI document is the source from which client hooks and validation schemas are generated.

Persistence

Drizzle ORM defines the stored data on the Express side.

Runtime rules

Game behaviour lives in the shared engine, not in either client's UI layer.

07API documentation

This project has an actual contract document rather than a hand-written endpoint list: the API is described in OpenAPI, and Orval generates React Query hooks and Zod schemas from it. That means the spec in the repository is both the documentation and the input to the client build. I have not published a rendered API reference on this site.

12Testing methodology and results

The CI workflow runs on every push and pull request. It installs dependencies from the frozen pnpm lockfile, typechecks the workspace, runs test:ci, executes benchmarks with BENCH_OUTPUT=reports/benchmark.json, then appends a generated summary to the job summary and uploads the reports directory.

The published run at commit 273658c on main passed in 33s, with the job taking 30s. The summary reports 18 tests, 18 passed and 0 failed. The typecheck step also passed before the tests and benchmarks ran.

13Performance measurements

Benchmarks were recorded on Node v24.22.3, linux/x64. The shared engine is measured in microseconds per frame for both clients:

  • Web engine — 5.153 µs/frame median, 8.359 µs/frame p95, 194,076 updates/sec.
  • Mobile engine — 4.052 µs/frame median, 28.69 µs/frame p95, 246,805 updates/sec.

The mobile engine has the lower median but a wider tail, with a 28.69 µs p95 against 8.359 µs on web. The full 1.39 KB report is in the test-and-performance-reports artifact.

14Security considerations

  • Supply-chain rules in pnpm-workspace.yaml add a check on dependency behaviour in the monorepo.
  • Generated clients and Zod validation mean unexpected response shapes are rejected rather than trusted.
  • No API keys or secrets are described as part of the game's client code.
  • Since there is no login, the web demo does not handle user credentials.

15Difficult technical challenges

Sharing game logic between Canvas and React Native without leaking rendering concerns into the engine was the main design problem. The second was type drift: keeping a server change from silently breaking a client. Generating hooks and Zod schemas from the OpenAPI document moved that failure to build time. Setting up a pnpm workspace that also encodes supply-chain rules was the third, and it is what made the multi-package setup feel deliberate rather than convenient.

16Engineering trade-offs

  • One shared engine: no duplicated rules, in exchange for care around platform-specific input and rendering.
  • Generated API code: an extra build step, in exchange for contracts that stay in sync.
  • Canvas on web: direct control for a render loop, in exchange for building UI affordances the DOM would give for free.
  • Monorepo: shared types and tooling, in exchange for more configuration than a single app.

17Known limitations

  • No published database schema or API reference; benchmarks cover the shared engine, not full client frame rate.
  • No authentication or account features described.
  • Clients depend on a code-generation step, so the OpenAPI document must stay current.

18Future development roadmap

Ideas I would consider, not promised features:

  • Publish the schema and a rendered API reference from the OpenAPI document.
  • Measure full client frame rate and input latency in addition to the engine benchmarks.
  • Expand the 18 automated tests to cover more shared-engine rules.
  • Document the generated-client build step for new contributors.

19Outcomes and measurable results

The browser game is playable from a public link. The result I can describe without exaggeration is a single engine serving two very different clients with a generated API contract between them. I have not measured retention or session length, so none of that is claimed.

20My contribution

I built Orbit Rush as a personal project: the shared engine, the React Canvas web client, the Expo mobile client, the Express and Drizzle server, the OpenAPI contract and the pnpm workspace setup. There was no separate team to attribute any of those parts to.
