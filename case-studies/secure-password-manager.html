Secure Password Manager

A browser password manager with AES-256 encryption, a generator, search and clipboard support — backed by a REST API built without a frontend framework.

01Project overview

This is the web counterpart to my Android password app. It stores entries with AES-256 encryption using CryptoJS, offers a password generator, search and clipboard support, and exposes full CRUD operations through a REST API. The front end is plain HTML, CSS and JavaScript, with no framework.

02The real problem

I wanted to build a web version of the Android password app to practice backend and REST API design. Using no frontend framework was deliberate: it forced me to handle state, events and rendering directly instead of relying on a library to hide those details.

03Target users and their needs

  • Someone who wants a simple browser-based vault with a generator and search.
  • They need create, read, update and delete to work predictably through the API.
  • They need the interface to be responsive and understandable without a design system behind it.
  • For me: a focused exercise in API structure and encryption on the server side.

04System architecture

05Technology selection and justification

  • Node.js and Express are a compact way to expose CRUD endpoints and keep the encryption step on the server.
  • CryptoJS provides the AES-256 implementation used for stored values.
  • Plain HTML, CSS and JavaScript remove framework overhead and make the exercise about the API and DOM behaviour.
  • REST keeps the operations visible: each vault action maps to a resource operation rather than a bespoke transport.

06Database schema / data model

07API documentation

The API is a REST service covering vault entry CRUD. I have not published a formal OpenAPI document or an endpoint table for it, so I am not listing routes I cannot verify here. The Express route definitions in the repository are the current reference.

08Authentication and authorization

No authentication or ownership model is described for this project, and I will not imply one. That is a real limitation for a password manager: encryption of stored values is not the same thing as user isolation. Any future version intended for sensitive use would need a clear account and key-management design before it could be taken seriously.

14Security considerations

  • Stored secrets are encrypted with AES-256 via CryptoJS.
  • Encryption runs on the server, so the raw crypto setup is not duplicated in the browser.
  • There is no published authentication or per-user isolation model, which is a genuine limitation for a password manager.
  • No security audit has been performed or claimed; treat this as a learning project rather than a production vault.

15Difficult technical challenges

Structuring a REST API by hand meant deciding resource shapes and error behaviour without a framework to suggest them. Applying encryption on the server while keeping the client simple meant being explicit about where plaintext exists and where it does not. Working without a frontend framework was the most educational constraint: state changes and DOM updates had to be written out rather than declared.

16Engineering trade-offs

  • No framework: full control and no dependency weight, in exchange for more manual DOM and state code.
  • Server-side encryption: simpler client, in exchange for a key-management question this version does not fully answer.
  • REST: visible, cacheable operations, in exchange for several round trips compared with a bespoke endpoint.
  • CryptoJS: quick to integrate, in exchange for relying on a library for the crypto primitive rather than a platform API.

17Known limitations

  • No authentication, per-user isolation or published key-management design.
  • No formal API documentation, test report or screenshots.
  • No published security review; not suitable as a real credential store.
  • No measured performance data.

18Future development roadmap

Ideas for a more serious version, not current work:

  • Design and document authentication plus per-user data isolation.
  • Publish an OpenAPI document and a test suite for CRUD and encryption.
  • Review key management and decide whether encryption should be client-side.
  • Capture real screenshots of the responsive interface.

19Outcomes and measurable results

The demo is hosted, and the walkthrough video shows the main flows. The concrete result is a working framework-free front end talking to an encrypted REST backend. I have not measured usage growth, latency or any security outcome, so none is claimed.

20My contribution

I built this as a personal project: the Express routes, CryptoJS encryption, storage layer and the plain HTML/CSS/JavaScript interface. It was a solo exercise in backend design, with no team or external reviewer involved.
