Case study / 04 / Security-minded Android

SecureVault

An Android password manager with biometric unlock and AES-256 encrypted local storage. The manifest has no internet permission, so vault data has no network path out of the device.

01Project overview

SecureVault is a native Android password manager that keeps everything on the device. It stores entries in an encrypted Room database, uses the Android Keystore for key material, and unlocks with fingerprint or face through the biometric APIs. The interface is built with Jetpack Compose and Material 3.

02The real problem

Most password managers I could find required an account and synced to a server. That is a reasonable model, but it is not what I wanted for a simple local vault: one device, no account, no background sync, and a clear reason to trust where the data sits. Removing the network from the design makes that promise much easier to keep.

03Target users and their needs

  • People who want credentials stored on a single Android device without creating an online account.
  • They need fast unlock on a phone they already trust, and an interface that is calm rather than alarming.
  • They need the app to work offline and not ask for network access.
  • They should understand the trade-off: local-only also means no automatic recovery if the device is lost.

04System architecture

05Technology selection and justification

  • Kotlin and Jetpack Compose for a native, low-friction Android interface.
  • Room with AndroidX Security gives an encrypted local database instead of raw files I would have to protect myself.
  • Android Keystore keeps key material in hardware-backed storage where the platform provides it.
  • Biometric APIs make unlock fast on a device the user already trusts.
  • MVVM separates vault state from the screens that display it.
  • No network permission is a design choice, not an omission: it makes the local-only promise enforceable by the OS.

06Database schema / data model

The model is deliberately small: a vault entry holds a label and account identifier with the secret stored encrypted, and the database as a whole is protected by encryption rather than by per-field hand-rolling. I have not published a table listing, so the Room entities in the repository are the exact schema.

Vault entry

Label, account identifier and the protected secret value.

Encryption

AES-256 applied to stored data through AndroidX Security.

Key material

Held by Android Keystore, not in app preferences or source.

Unlock

Biometric prompt gates access to the decrypted vault.

07API documentation

There is no HTTP API. The internal boundary is the repository that wraps Room, and there are no remote endpoints to document. Publishing an API reference would be misleading for this app.

08Authentication and authorization

There is no account system. The relevant mechanism is local authentication: the biometric prompt verifies that the person holding the device can unlock the vault, and Android Keystore controls access to the key. That is different from online authentication and gives no recovery path through a server. I have not added roles or sharing because the app is single-device by design.

14Security considerations

  • No internet permission in the manifest: the OS prevents network access for the app.
  • AES-256 encryption for stored vault entries via AndroidX Security.
  • Key material kept in Android Keystore rather than in app data or source.
  • Biometric unlock through the platform prompt, not a custom PIN implementation.
  • No published audit: treat this as an implementation description, not a security certification.

15Difficult technical challenges

Getting key handling right was the main challenge: the encryption key has to survive app restarts without living somewhere readable in app data, which is what the Keystore is for. The second was making biometric unlock feel immediate while still going through the platform prompt rather than a home-grown gate. Treating "no internet permission" as a hard constraint shaped every other decision, because no feature could quietly depend on a network call.

16Engineering trade-offs

  • Local-only: strong privacy story, in exchange for no sync across devices and no server-side recovery.
  • Platform encryption APIs: less custom crypto, in exchange for Android-specific behaviour.
  • Biometric unlock: fast and familiar, in exchange for depending on device hardware and OS support.
  • No account: no credential database to protect, in exchange for the user owning all backup responsibility.

17Known limitations

  • Android only, with no browser demo.
  • No sync, cloud backup or account recovery.
  • No published audit, test report or screenshot set.
  • Biometric unlock depends on the device supporting it.
  • Local-only means a lost device can mean lost credentials.

18Future development roadmap

Possible next steps, not commitments:

  • Publish an independent security review before describing the app as audited.
  • Add a documented, user-controlled encrypted backup and restore path.

19Outcomes and measurable results

The app is published on Google Play. The outcome I can state precisely is an offline vault with encrypted storage, Keystore-backed keys and no network permission. I have not measured installs, retention or incident rates, and no security result beyond the implemented design is claimed.

20My contribution

I designed and built SecureVault as a personal project: the Compose UI, MVVM layers, encrypted Room storage, Keystore and biometric integration, and the decision to omit internet permission. It was a solo build, with no security team or external reviewer involved.
